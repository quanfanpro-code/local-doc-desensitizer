# 全面复核与修复 — 需求文档（2026-07-25）

## 背景

用户要求对「本地文档脱敏工具」做一次全面复核，确保没有致命 bug，顺手完成可实现的优化，最后同步更新 readme.md。

## 复核范围

主程序（app.py / ner引擎.py / 脱敏处理器.py / 格式保持器.py / 文档解析器.py / mineru桥接.py / _docx_xml工具.py）、启动器.py、维护工具、开发测试，共约 4200 行。

## 发现的问题清单

### 致命 / 高优先级

| # | 位置 | 问题 | 后果 |
|---|------|------|------|
| 1 | 脱敏处理器.py `处理文件列表` | `文本脱敏()` 的返回值（脱敏后文本）被丢弃；扫描版 PDF 走 `生成脱敏md()` 时重新从 PDF 提取文本，而扫描版 PDF 本来就没有文字层 | **扫描版 PDF 输出的 md 文件几乎是空的**，OCR 识别 + 脱敏的成果全部丢失 |
| 2 | 脱敏处理器.py `处理文件列表` | NER 调试日志默认对每个文件开启，把**原始敏感全文**写到输出目录的 `*_NER调试.log`；且 `文本脱敏()` 抛异常时 `关闭调试日志()` 不会执行，文件句柄泄漏 | 脱敏工具反而在输出目录留下未脱敏的原文；句柄泄漏 |
| 3 | app.py `start_desensitize` | 无论当前是本地还是在线模式，检查的都是本地 LM Studio 状态 | 在线 API 模式下永远误报「LM Studio 未就绪」 |
| 4 | app.py `start_desensitize` | 扫描版 PDF 的真正前提是 MinerU OCR 引擎，但代码检查的是 LM Studio | MinerU 没装时 GUI 放行，处理到一半才逐个文件失败 |

### 中优先级

| # | 位置 | 问题 | 后果 |
|---|------|------|------|
| 5 | app.py `run_desensitize` / `run_restore` | CTkProgressBar 取值范围是 0~1，代码却 `configure(value=当前/总数*100)` | 进度条处理第 1 个文件就拉满，失去指示意义 |
| 6 | ner引擎.py `注册自定义映射` | 同一代号的简称碰撞超过 10 个（①~⑩用完）后**静默放弃注册** | 第 11 个起的原文不会被替换，敏感信息静默泄露 |
| 7 | 脱敏处理器.py / 格式保持器.py | 只有绝对包导入 `from 主程序.xxx`，直接运行 `python 主程序/app.py` 会 ImportError 崩溃 | 只能走启动器.py，健壮性差 |

## 边界条件

- 不改变脱敏/还原的核心算法和映射表文件格式（保证旧映射表仍可还原）。
- 不做 speculative 的新功能；优化仅限上表。
- settings.json 中明文 API 密钥属于既有设计，本次只在 readme 中提示，不改存储方式。

## 验收标准

1. 上表 1~7 全部修复，8~11 顺手清理。
2. 每个修复有对应单元测试；`python -m pytest 开发测试 -v` 全部通过。
3. readme.md 更新：扫描版 PDF 前提改为 MinerU、新增调试日志开关说明、更新记录追加本次条目。
