## 二、用户与使用场景

面向现有 Windows 文档脱敏工具的使用者，沿用已有文件选择和处理入口。机构名称可能出现在正文、表格、页眉页脚等位置；简称可能在后文才定义，也可能没有显式定义。

重点研究以下场景：

1. 有“以下简称”等明确声明，或通过表格列出全称与简称。
2. 未声明的字号、两三个字的简称、英文缩写，以及无法由机构后缀枚举得到的别称。
3. 全称与简称相隔多段、跨模型分段，甚至先简称后全称。
4. 同一机构有多个名称；不同机构共用相同简称；简称与普通词重名。
5. 文档只出现简称，无法从原文确定其全称。
6. 模型只识别出部分机构、返回异常、不可用或无法确定某个名称。
7. 文档提取、实际写回或再次打开后，敏感信息仍有残留。
8. 脱敏映射保存后重新加载，还原时需要保留原来使用的全称或简称。

这些是研究和验收候选场景；具体自动处理规则仍需澄清，不能把候选场景等同于已批准的实现方案。

## 三、已确认的完整范围与先后顺序

### 1. 两个仓库的全面比较

比较定位、实际工作流程、模型与规则的分工、词典结构、名称与简称关系、替换和还原、文件支持、结果检查及维护方式。

每项借鉴建议应说明：对方怎样实现、本库目前怎样实现、解决什么问题、有什么局限、是否适合引入。指出双方各自的优势和缺陷。

### 2. 首先解决机构名称与简称检测

完整追踪本库的文本提取、分段、提示词、模型输出解析、简称候选产生、上下文判断、全称关联及补漏流程。

重点评估：

- 任意简称能否进入识别流程，是否被正则、黑名单或长度规则提前排除。
- 模型能否取得所需上下文，已有机构信息是否有助于后续识别。
- “这是机构名称”和“属于哪家机构”是否混为同一个判断。
- 相似名称、上下级机构及同名简称是否被错误合并。
- 模型部分成功后，其他检查是否仍能发现遗漏。
- 同一简称在不同位置的含义不同时，能否避免全局误替换。

### 3. 其他敏感信息检测也须完成

检查现有其他敏感信息类别，包括人名、地址和各类固定格式信息。根据实际代码及样例补齐遗漏、减少误报，不能仅堆叠宽泛正则。

追溯 datamask 声称借鉴的 GitHub 项目；核实具体文件、规则、词典、验证方法和使用许可。比较本库现有词典来源，区分可以直接复用的内容、需要中文场景调整的内容，以及尚无证据的来源声明。

日期、金额等类别的具体启用方式，应结合现有设置和业务需要确认；“纳入研究与完善范围”不等于擅自将所有类别默认强制脱敏。

### 4. 完成替换、文件写回、复查和还原

检测改进须最终作用于实际输出文件。检查映射一致性、最长名称优先、替换边界、Word 跨格式片段、Excel 单元格提取与写回等实际行为。

研究同一机构的多个称呼如何关联，同时保留各称呼的原文，以支持保存映射、重新加载后的准确还原。检查处理后的残留，不得把“程序运行成功”直接等同于“脱敏完整”。
