# Excel 读取优化需求

日期：2026-09-18。用户明确要求使用需求优先工作流，完全自主决策，完成后提交并推送 main，不开其他分支。阶段检查点由这次明确授权覆盖，六阶段及验证照常执行。

## 背景与使用场景

注册会计师批量脱敏 Excel，需要检测公式计算出来的机构名称、简称及数字，并保留还原能力。此前逐个单元格读取 Text 和 Value2，每次读取原件、输出复查均新建 Excel。实测 5000 个公式约 28.36 秒，批量取值原型约 2.62 秒；10 个小文件复用实例原型约 3.09 秒。此处是原型证据，正式实现必须重新计时。

## 严苛追问与自主决定

- 目标究竟是更快提取还是更准确脱敏？在现有检测、替换和还原不退化前提下减少读取耗时，不能跳过公式重算。
- 为什么不直接使用 OfficeCLI？已验证其能计算常见公式，但缓存与新算值需分开读取，函数兼容性仍与原生 Excel 不同。单文件可更快，10 文件独立进程约 7.08 秒，慢于复用 Excel 原型。当前无需更换计算引擎。
- 一次任务怎样划分？一次“处理文件列表”及其中原件读取、输出复查和补做后重读共享一个专属隐藏实例；文件及映射仍逐个独立。
- 哪些结果不能遗漏？文字、零、False、空字符串、跨表引用、中文表名、单格与多格均须正确；错误值及不可用计算不冒充正常文本。
- 失败后是否继续交付？沿用既定约定：可用输出及映射照常保存，缓存只能作为带未完成说明的后备，不能因有缓存而声称复算成功。
- 大范围读一次是否足够？不够。稀疏公式不能把整张表搬进内存；限制每次区域大小，并避免解析时人为填满空白区域。
- 会不会影响用户正在使用的 Excel？只操作 DispatchEx 创建的实例及本任务工作簿；关闭不保存原件，禁用宏、事件、外部链接更新。
- 取消和失败是否释放资源？正常结束、异常与取消都要尝试关闭本任务工作簿及实例，释放 COM；关闭失败必须可见，不扣住已生成结果。
- 是否需要新依赖、并行或全局驻留？均不需要，复用已安装的 Excel、pywin32、openpyxl；任务结束退出。
- 本轮交付是否包含之前成果？包含本对话已完成、尚未提交的机构简称及全面脱敏改进；不得丢弃。

## 范围与验收

1. 批量读取公式值，并限制单次传输区域；相距很远的公式仍可正确读取。
2. 同批任务及复查复用实例；无公式文件不启动 Excel；独立调用仍可用。
3. 保持新值优先、错误标记、映射、公式还原、数字类型及原文件哈希不变。
4. 验证真实 Excel 与真实处理入口；故障注入验证缺 Excel、关闭失败、取消；完整现有回归通过。
5. 对 8、1000、5000 个公式和 10 个小文件重新计时，至少 3 次报告中位数，核对每个结果。5000 公式读取较旧实现至少减少 70% 耗时；不把读取优化称为整个 LLM 流程同幅提速。
6. 同步 README、设计、计划、审查及交付状态，扫描敏感配置后提交 main 并核实远端提交一致。

## 边界和风险

不新增 OfficeCLI 后端、不改模型及识别策略、不做并行 Excel、不更新外部数据、不发布安装包。原生重算期间无法即时中断，同步 COM 卡死的超时隔离不在本次实现中；分块间与文件间响应取消。大文件仍由 openpyxl 加载已存储单元格，内存不是无限。

## 调研依据

此前本机会话已核验 OfficeCLI 1.0.151 和 Microsoft Excel 16.0 Build 20326.0，复用同一天原始测量。微软建议一次读写大块数据：[性能指引](https://learn.microsoft.com/en-us/office/vba/excel/concepts/excel-performance/excel-tips-for-optimizing-performance-obstructions#read-and-write-large-blocks-of-data-in-a-single-operation)。原生重算使用 [CalculateFullRebuild](https://learn.microsoft.com/en-us/office/vba/api/excel.application.calculatefullrebuild)，只读打开及链接控制见 [Workbooks.Open](https://learn.microsoft.com/en-us/office/vba/api/excel.workbooks.open)。
