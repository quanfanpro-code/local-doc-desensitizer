# 机构简称与全面脱敏改进：方案设计

日期：2026-09-18。状态：方案与实施计划已批准，代码及验收已完成；实际结果另见实施交付记录。

## 1. 已确认的要求

机构名称、尤其无固定规律的简称优先。两个仓库的全面比较、GitHub 上游来源核查、其他既有敏感类别、文件写回、保存后复查及准确还原都在范围内。优先级只决定先后，不删减工作。

每份文件独立识别、关联和编号；不借用其他文件的信息。确定指机构但原文没有全称的简称独立脱敏，不编造全称。主要真实验证模型为用户指定的 Qwen3.8-27B，保留现有本地及在线接口选择。不新增人工逐词确认的使用流程。

当前核查版本：datamask 为 a7339baaac2206b44e58412ff6f98e2b2fe209aa；本库为 576e2668c351d113d2f0da4322154652c00f3aee。当日再次查询远端，两者默认分支提交未变。上述提交为改前基线；改进代码在本地 codex/org-alias-detection 分支。

## 2. 已查明的问题决定了什么必须改

| 已有证据 | 设计要求 |
|---|---|
| 简称专门复核只发送候选词，没有原句、表头或机构关系；候选还受长度、汉字和黑名单限制 | 原文中的任意简称都能由模型发现；提供上下文，规则候选只补充、不限制模型范围 |
| 已知实体被要求跳过，主要输出只有名称和类型 | 保留已知机构作为理解上下文的依据；继续判断每次出现的位置及含义 |
| 根据名称全局替换，同词普通用法也被替换 | 识别与写回都使用出现位置，不能识别时看上下文、替换时又丢掉上下文 |
| 名称清洗和包含匹配可能把相似名称归入同一机构 | 单独判断“是否机构”和“属于谁”；相似名称只产生关联候选，不能直接合并 |
| 模型只返回部分机构时，明显机构补漏可能不执行 | 模型发现、规则补充、覆盖核对互相补充，不因已有少量输出而关闭后续检查 |
| 全称和显式简称共用一个代号后无法逐处还原 | 机构关联与原文写法分别保存；新映射保存、重载后仍保留原称呼 |
| Excel 数字及纯数字文本在提取时被过滤，实际输出保留号码 | 规则检查原始单元格，保留类型和位置；模型输入优化不能删掉规则所需数据 |
| 对方 Word 跨格式片段重复替换、页眉遗漏；扫描复用同样规则也会漏 | 复用本库已有多格式基础，修复定位写回；复查实际文件并加入不同角度的检查 |

|---|---|---|

| 定位完整性 | 不适用 | 摘录均来自原文，但其中 6 条摘录含同名重复，不能单凭摘录唯一定位 |
| 本次单次耗时 | 65.063 秒 | 93.945 秒 |

两次服务响应的 content 都混入了思考文本。直接 json.loads 的探查失败不等于原程序失败：离线使用本库现有严格解析器，第一条响应成功得到 10 个名称。第二条响应按结束标记后的正式对象核对；未来对象格式需明确解析和结构验证，不能照搬只抽取数组的解析器。

本次请求仅用于方案探查，最大输出设置为 4096，两次 finish_reason 均为 stop。时间包含当前服务运行情况，不能推断日常整份文档耗时。没有上传真实客户材料。保存的探查脚本和结果不含 API Key；交付记录只展示最终结构和核对结果。

核心启示：本样例不支持“简称普遍分不清”的推断，却明确暴露了按词替换、漏报位置及定位不唯一的问题。应先解决这些可验证的实现问题，再讨论尚未出现的业务取舍。

## 4. 两个可行方案

两个方案都包含位置替换、关系关联、规则完善、实际文件复查和准确还原，区别主要在模型怎样读取一份文件。

| 比较维度 | A：先整理文内机构，再逐段核对所有出现位置（已选择） | B：短文整篇联合识别，长文转用 A |
|---|---|---|
| 处理方式 | 首轮覆盖全部原文，整理称呼和关系；第二轮带着文内机构资料重新核对全部原文，发现新简称、区分普通用法、确定位置 | 能安全容纳输入与输出的短文，整篇一次返回机构和位置；超出预算的文件走 A；同样执行保存后复查 |
| 优点 | 长短文沿同一条主流程，后文出现的全称也能帮助前文简称；便于逐段检查覆盖及单独重试 | 短文可能减少模型调用，单次直接看到全文；长文仍有完整处理路径 |
| 实现和维护 | 需要文内机构资料、两轮覆盖记录及局部复核；流程统一 | 在 A 之外维护整篇路径、长度和输出预算判断，两条路径要保持同样行为 |
| 时间与调用代价 | 通常比短文单次联合识别多一轮；局部复核只处理有问题的位置 | 短文可能省一轮；截断或切换后可能重做，省时幅度必须实测 |
| 风险 | 首轮遗漏关系可能影响后续，因此第二轮必须允许发现新机构，不能只在已有名单里选择 | 能装进上下文并不保证逐处结果齐全；本次短文联合结果仍漏一处全称 |
| 兼容和依赖 | 复用现有接口；分段大小按模型可用输入、输出预算调整，无须引入新引擎 | 同样兼容，但需要更多模型预算探测与分支验证 |
| 测试难度 | 覆盖跨段、前后倒序、名单遗漏、每段完成与重试 | 除 A 的测试，还须比较整篇与分段的一致性、临界长度及超限切换 |
| 可逆性 | 核心数据和写回独立，以后可增加整篇优化 | 可关闭整篇优化回到 A，已保存映射不应受影响 |

2026-09-18，用户回复“A”，选择先整理当前文件的机构与简称关系，再带着这些信息逐段核对全部原文，最后复查实际输出。该选择确定总体路线，不重复提问。

推荐依据是用户已经明确先把检测做好，而统一的两轮流程更便于验证“全文确实看过、后文关系确实用于前文、补漏确实执行”；并非已经证明 A 的模型准确率高于 B。当前不增加短文整篇识别分支。以后是否增加 B 的优化，须看正式样例中的质量与时间差异，不是本次默认扩展。

接口目前报告 131072 令牌上限，这不等于全部可用于输入，还须预留提示词、机构资料和输出。超长文件不能截去后部或只传前若干个机构。先按稳定段落及表格结构分段，再按预算调整；机构资料过多时按文内证据分组核对并覆盖全部组，不静默截断。当前不切换未验证的 256K 接口，也不假设关闭思考或并发能提高效果。

长上下文位置效应可参考 [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)，用于安排首部、中部、尾部互换的测试；该论文不是本次 Qwen 模型能力的直接证据。

## 5. 推荐方案的数据流

原文件 → 带位置的原文块 → 首轮发现称呼和关系 → 文内机构资料 → 全部原文逐段复核 → 本地核对名称、位置及覆盖 → 按位置生成替换 → 保存新文件 → 重新读取并复查 → 输出文件和独立还原映射。

### 5.1 保留原文和位置

原文块至少保存：文件内编号、实际位置、原始文本和必要上下文。模型看到的是便于理解的内容，写回依据始终是未经改写的原文。

- Word：保留部件、段落、表格单元格及各文本片段对应关系，覆盖既有页眉、页脚、脚注等读取范围。
- Excel：保留工作表、行列、单元格类型及值；同列标题、同行交易对手等作为上下文。多级或合并表头按实际结构提供；不能把所有单元格压成一串，也不能因为含金额就删掉整格机构名称。
- PPT：保留页、形状、表格单元格和文字片段位置。
- 文字 PDF：保留页和文字坐标，模型判断对应到具体文字区域。扫描 PDF 继续走已有识别后输出 MD 的路径；不擅自承诺恢复扫描件原版面。
- TXT、MD：保留原文字符位置、换行和编码信息。

原文若做全半角、空格、大小写等识别归一，必须另保留归一前后的位置对应；不能用清洗后的字符串覆盖原文。复用现有解析库，不为此引入新的文档平台。

### 5.2 首轮发现机构和关系

首轮读取全部原文块，允许输出有后缀全称、任意简称、英文缩写和没有全称的机构称呼。名称须能在原文定位，关系须附原文依据。

“甲公司（以下简称乙）”等规则帮助发现明示关系；它们不是简称发现的入口门槛。含“和”“联合”、只有两个字、没有汉字等条件都不能直接否定机构。

母公司、子公司、关联公司保留不同主体。同一字符串可以在不同位置指不同主体，数据结构不能只有 name → entity 的单值对应。没有全称的简称独立建项；只是关系不确定，不能变成“不脱敏”。单纯字面相似和去后缀后的相同短词不能当作合并证据。

### 5.3 第二轮核对全部原文

带着本文件机构资料、原句、相邻段落及表头重新查看所有块，不限于首轮命中的句子，也不限于正则生成的候选。明确要求寻找尚未发现的机构简称，判断每一次出现是机构还是普通用法，并补充关系和位置。

如果新发现的关系会影响已经核对过的位置，只重新核对相关原文和候选；记录已处理内容，避免无休止重复。完整覆盖是一项程序可检查的事实，不把“模型说处理完了”直接当成覆盖证明。

### 5.4 程序核对位置，不盲信模型计数

模型返回原文块编号、原词、所属机构和能定位到该次出现的摘录。程序验证原词及摘录确实存在、所属机构有效，并计算原文字符位置。相同段落中有重复词时，先排除已确认全称内部的嵌套简称；仍不唯一时，用程序生成的逐处编号和局部上下文让模型选择。

已知名称在原文的所有出现都作为核对候选，逐处区分“已确认机构”“已确认普通用法”“尚未处理”；这不是把已知名称全局替换。本次宁波全称位于机构资料中、但未返回出现记录，便可由覆盖差异发现。未进入机构资料的漏词仍须依靠第二轮开放发现及输出复查，不能说上述核对包办一切漏检。

多个识别器命中同一位置时统一合并；完整机构名内部的地名或短名不能重复覆盖。不同类别的有效性、字段标签和上下文共同解决冲突，避免纯长度决定类别。

命中位置与识别依据分离的结构，可参考 [Presidio RecognizerResult](https://github.com/microsoft/presidio/blob/f251c513e8aad6820e9b2a44983ebf3a93637b07/presidio-analyzer/presidio_analyzer/recognizer_result.py)。上下文中的实体标记与针对性核对思路可参考 [GPT-NER](https://aclanthology.org/2025.findings-naacl.239/)；其发表指标不能转用于本项目。

## 7. 写回、复查及失败处理

写回只处理核准位置，从后往前修改，避免偏移失效。Word、PPT 不再按修改后总长度把整段文字重新均摊到格式片段，保留未修改内容的格式；跨片段名称只替换一次。Excel 对敏感数字单元格写入代号，映射保存原值和类型，还原后核对类型；公式与显示结果分别处理，不能盲改公式字符串。

PDF 必须在对应位置真正移除原文内容，不能仅画遮挡；保存到不同的新输出，重新打开核对文字与版面。已实际调用当前 PDF 函数，复现 ValueError: save to original must be incremental。相同单页样例采用不同新路径、普通保存及清除无用对象后，可重新打开，原号码不再存在，代号存在；这只验证保存方向，不代表全部 PDF 版面已通过。不能直接改成增量保存而忽略原内容清除验证。参数依据见 [PyMuPDF Document.save](https://pymupdf.readthedocs.io/en/latest/document.html#Document.save)。

Excel 也已复现：原公式 ='星河'!A1 被当前替换函数改成 ='[公司1]①'!A1，但实际工作表仍叫“星河”，引用因此失配。没有缓存的公式用 data_only 读取为 None；本机 Microsoft Excel 的独立隐藏实例实际读取出全称、拼接简称及数值结果，原始样例哈希未变。

据此确定 Excel 处理方式：普通计算公式及其引用保留；识别同时使用原值、公式文字常量和实际显示值。涉及机构名称等敏感文字的公式单元格，优先对文字常量作定位替换；若敏感结果由拼接或计算产生、无法在公式常量中安全替换，仅将该命中单元格写为脱敏后的值，并把原公式和类型存入还原映射。还原时恢复公式。不得将整张表公式统一转值，也不得把工作表引用当作普通文字替换。使用本机 Excel 时仅操作独立实例及任务文件，不刷新外部链接、不操作用户打开的工作簿；没有可计算结果时如实记录该单元格覆盖情况，仍交付其他处理结果。

| 写回或保存异常 | 根据实际异常修复位置、文件保存或格式处理问题，不通过重新跑识别器假装已解决 |
